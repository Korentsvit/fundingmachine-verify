In both releases `DetachedTimestampFile.deserialize` (`opentimestamps/core/timestamp.py`) reads the file's hash operation with `CryptOp.deserialize`, which accepts only the tags in `CryptOp`'s table. `Op._register_op` (`opentimestamps/core/op.py`) enters a class in the table it is called on and in each table above it. 0.4.5 registers `OpKECCAK256` (tag 0x67) with `@CryptOp._register_op`, so it is in `CryptOp`'s table and in those of `UnaryOp` and `Op`, the operations a timestamp may contain. 0.5.0 registers it with `@UnaryOp._register_op`, so it is in `UnaryOp`'s and `Op`'s tables only. V-70's wording ("as an operation inside a timestamp only") already says this. Neither release's files carry a change log, and the code does not say why the registration changed: the earlier row's "apparently as part of reworking how a file is hashed" was a guess at the reason, and the decision does not depend on it.
